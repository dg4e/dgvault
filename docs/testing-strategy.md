# dgvault: Testing & Quality-Gate Strategy (Critic-owned)

This document defines how every feature in `plan.md` is verified before it counts
as "done". It is authored in Phase 0 so that Performer/Composer can write code
against a known test contract rather than retrofitting tests later.

## 1. Test tiers

| Tier | Scope | Lives in | Runs in CI |
|------|-------|----------|-----------|
| Unit | Pure `lib/core` logic (crypto, KDF, generator, merge, audit, placeholders) | `test/core/**` | yes |
| Golden round-trip | KDBX read → model → write → byte/semantic compare vs reference | `test/golden/**` | yes |
| Vector | Known-answer tests: Argon2, AES/ChaCha, HMAC-SHA1 TOTP, Steam TOTP | `test/vectors/**` | yes |
| Widget | UI screens/widgets in isolation | `test/ui/**` | yes |
| Integration | Cross-layer flows (unlock → decrypt → search) | `integration_test/**` | best-effort |
| Platform smoke | Channels (biometric/autofill/ssh) behind fakes | `test/platform/**` | yes (fakes) |

Platform-native code (Keychain, AutoFill, SSH agent) is exercised through fakes
in `test/platform`; the real channel is validated manually per release. CI must stay green headless - no test may require a device.

## 2. Golden round-trip contract (KeePass interop: the critical gate)

Goal: a database written by dgvault opens in KeePassXC / KeePass 2.x and vice
versa, and a read→write cycle is lossless.

Fixtures live in `test/golden/fixtures/` (see that dir's README):
- `aes-argon2.kdbx` - KDBX4, AES-256, Argon2id (password: `correcthorsebatterystaple`)
- `chacha-argon2.kdbx` - KDBX4, ChaCha20, Argon2id
- `aes-aeskdf.kdbx` - KDBX4, AES-256, legacy AES-KDF (backward compat)
- `with-attachments.kdbx` - binaries, custom fields, custom icons, history
- `keyfile.kdbx` + `keyfile.key` - composite key (password + key file)

Each fixture has a sidecar `*.expected.json` describing the decrypted logical
content (groups, entries, fields, tags, history depth, attachment hashes). The
golden test:
1. opens the fixture with its credentials,
2. asserts decrypted content equals the sidecar JSON,
3. re-serializes, re-opens the output, and asserts the logical content is
   byte-for-byte stable across a second round-trip (write determinism where the
   format allows; otherwise semantic equality + valid re-decrypt).

Fixtures are generated by KeePassXC CLI (`keepassxc-cli`) so they are
independent of our own writer - preventing "tests pass because they validate our
own bug." Generation steps are recorded in `test/golden/fixtures/README.md`.

## 3. Crypto known-answer tests (no hand-rolled primitives)

- Argon2id: RFC 9106 / reference test vectors.
- AES-256-CBC + HMAC, ChaCha20: NIST / RFC 8439 vectors.
- TOTP: RFC 6238 Appendix B vectors; Steam: published Steam-guard alphabet vectors.
Any crypto code that cannot be backed by a published vector is REQUEST_CHANGES.

## 4. Security review checklist (Critic sign-off required for these features)

Applied to: crypto, KDF, secure storage, PIN/biometric unlock, duress PINs,
delete-on-fail, clipboard, import/export.

- [ ] Master secret never written to disk in plaintext (grep for persistence of raw keys).
- [ ] Derived keys held only in memory and zeroed on lock (no lingering `Uint8List`).
- [ ] PIN/biometric only *unwrap* an OS-keystore-held DB key - they are not the key.
- [ ] Duress "delete all" is irreversible by design and guarded from accidental trigger; covered by a test that asserts data is gone.
- [ ] Duress "dummy DB" is indistinguishable from a real unlock to an observer.
- [ ] Clipboard auto-clear actually clears (and clears on app background).
- [ ] Encrypted CSV export cannot be opened without the passphrase (round-trip + negative test).
- [ ] No secrets in logs.

## 5. Definition of done (enforced by the gate)

A `plan.md` checkbox may flip to `[x]` only when, for that feature:
1. code exists under the correct `lib/` layer,
2. the test tiers above that apply are present and pass `flutter test`,
3. `flutter analyze` is clean,
4. security-sensitive features have a recorded security review,
5. interop features pass the golden round-trip.

## 6. Toolchain status (Round 2 honesty note)

The build toolchain (Flutter/Dart) is **not yet installed in this environment**
and no scaffold/code exists on `master` yet. Therefore no `flutter test` run can
be claimed as green at this point - doing so would be fabricated. This gate and
strategy are pre-positioned so that the moment Composer lands the scaffold and
Performer lands the core, tests are authored against this contract and CI
enforces it. Until then, any agent voting CONSENSUS: YES on a *code* task is
asserting something unverifiable.
